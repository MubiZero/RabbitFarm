# Передача хозяйства фермы другому владельцу

## Контекст

Ферма (`Farm.owner_id`) сейчас закрепляется за пользователем один раз — при
регистрации — и сменить владельца нечем. Проект уже мульти-тенантный:
`Invitation` заводит новых работников по коду, `staffService.updateMember`
меняет роль и доступ существующих работников (`manager`/`worker`), но
владельца этим методом менять запрещено намеренно — «иначе ферма может
остаться без хозяина или работник поднимет сам себя».

Нужен явный флоу передачи владения — целиком другому активному работнику
той же фермы.

## Решение

Передача — мгновенное действие владельца, без отдельного подтверждения со
стороны получателя. Это осознанный выбор, а не упрощение: получатель уже
авторизованный участник той же фермы, а не посторонний по коду (как в
`Invitation`), и в проекте нигде больше нет асинхронных pending-состояний
для действий владельца над своими работниками — смена роли, сброс пароля,
отзыв доступа тоже происходят мгновенно, только под `authorize(['owner'])`.
Подтверждение — на стороне клиента, диалогом.

Получателем может быть **любой активный работник фермы** — и `manager`, и
`worker`; сужать список до менеджеров смысла нет, владелец сам решает, кому
доверяет. Прежний владелец после передачи **становится `manager`** —
остаётся в ферме с почти полным доступом, но без права управлять составом и
передавать хозяйство дальше. Дальнейшую судьбу своей роли (понизиться до
`worker`, деактивироваться) он определяет сам через существующий
`PATCH /staff/:id`.

## API

`POST /staff/:id/transfer-ownership`

- `:id` — id получателя (существующий работник **той же** фермы).
- Тело запроса не нужно.
- `authorize(['owner'])` — только текущий владелец.
- Ответ: `200` с обновлённым получателем (`{ id, email, full_name, role }`).

Ошибки:
- `404 MEMBER_NOT_FOUND` — получатель не найден в этой ферме, неактивен, или
  уже владелец (условие `role != 'owner'` в поиске само исключает попытку
  «передать самому себе» — тем, кто уже владелец, найти нельзя).

## Логика (`staffService.transferOwnership(farmId, currentOwnerId, newOwnerId)`)

1. Найти получателя:
   ```js
   const newOwner = await User.findOne({
     where: { id: newOwnerId, farm_id: farmId, role: { [Op.ne]: 'owner' }, is_active: true }
   });
   if (!newOwner) throw new Error('MEMBER_NOT_FOUND');
   ```
2. Одной транзакцией (по образцу `authService` — `Farm.update` +
   `User.update` в одной транзакции при регистрации):
   - `Farm` (по `farmId`) → `owner_id: newOwnerId`.
   - `newOwner` → `role: 'owner'`.
   - `currentOwner` (`req.user`, уже загружен `authenticate`) → `role: 'manager'`.
3. `logger.info('Ownership transferred', { farmId, fromUserId: currentOwnerId, toUserId: newOwnerId })`
   — по аналогии с логированием остальных действий в `staffService`.
4. Токен-инвалидация не нужна: `authenticate` читает `role` из БД на каждый
   запрос (`User.findByPk` в middleware), новые права действуют со
   следующего запроса без перевыпуска токенов — так же, как при обычной
   смене роли через `updateMember`.

`Farm` не входит в `TENANT_MODELS` (это сама единица аренды, а не
арендуемая строка), поэтому tenancy-хук на `Farm.update` не действует и
никакого `tenantScope` указывать не нужно.

## Клиент (Flutter)

- На карточке работника (экран состава фермы) у владельца — пункт меню
  «Передать хозяйство», видимый только для активных работников и только
  когда экран открыт владельцем.
- Диалог-подтверждение: «Ферма перейдёт {имя} — вы станете менеджером.
  Продолжить?» / Отмена.
- После успешного ответа — обновить локально закэшированный профиль
  (роль пользователя сменилась на `manager`), UI переключается на
  представление менеджера без перелогина.

## Тесты (backend, integration)

- Успешная передача: `farm.owner_id` меняется, у получателя `role='owner'`,
  у бывшего владельца `role='manager'`.
- Вызов не-владельцем (`manager`/`worker`) → `403`.
- Получатель не найден / не в этой ферме / неактивен / уже владелец → `404
  MEMBER_NOT_FOUND`.
- После передачи бывший владелец теряет доступ к владельческим ручкам
  (`POST /staff/invitations`, `PATCH /staff/:id` и т.п.) без повторного
  логина — проверяет, что роль реально читается заново, а не кэшируется в
  токене.

## Не входит в объём

- Явный accept/отказ со стороны получателя.
- Передача пользователю, ещё не состоящему в ферме (для этого сначала нужно
  приглашение).
- Ограничение частоты передач или история прошлых владельцев.
