# Развёртывание в Coolify

Стек описан в [`docker-compose.coolify.yml`](../docker-compose.coolify.yml) и состоит из четырёх сервисов:

| Сервис | Что это | Домен |
|---|---|---|
| `db` | MySQL 8 только для этого проекта, данные в томе `db-data` | нет, доступен лишь изнутри стека |
| `minio` | Хранилище загруженных фото (S3-совместимое), данные в томе `minio-data` | нет, доступен лишь изнутри стека — консоль наружу не выставлена |
| `api` | Node-бэкенд, миграции накатываются при старте | `api.<ваш-домен>` |
| `web` | Flutter-приложение, собранное под web и отдаваемое nginx | `<ваш-домен>` |

Пароли и секреты в репозитории не хранятся: Coolify генерирует их сам при первом
деплое по «магическим» переменным `SERVICE_*` и держит у себя.

## Текущий стенд

Проект `rabbitfarm` в Coolify на `cool.mubi.dev`, окружение `production`,
сервер `localhost` (207.180.237.97). **Стенд собран из отдельных ресурсов, а
не из `docker-compose.coolify.yml`** — сверено через API Coolify 2026-09-13:

| Ресурс в Coolify | Тип | Что важно знать |
|---|---|---|
| `rabbitfarm-api` | Application (Dockerfile) | том `/app/logs`; боевая база называется `default`, не `rabbitfarm` |
| `rabbitfarm-web` | Application (Dockerfile) | Flutter-сборка под web |
| `rabbitfarm-db` | Database (managed MySQL 8) | имя базы `default`, пользователь `mysql` |
| `rabbitfarm-minio` | Service (шаблон MinIO) | образ с `quay.io`, бакет `rabbitfarm-uploads`, тома `minio-data` и `minio-backups` |
| `rabbitfarm-redis` | Database (managed Redis) | кэш сводки платформы |

Отсюда следствие, на которое легко попасться: правка
`docker-compose.coolify.yml` **прод не меняет**. Файл остаётся референсом и
основой для прод-подобного стека локально; боевые настройки живут в панели.

Домены сервисов:

| Сервис | Домен |
|---|---|
| `web` | `https://rabbitfarm.mubi.dev` |
| `api` | `https://api.rabbitfarm.mubi.dev` |

Оба домена ведут A-записями на `207.180.237.97`, сертификаты выпущены
Let's Encrypt, `http` отвечает редиректом на `https`.

Если будете добавлять новый домен: заводите запись с DNS-only (серое облако
в Cloudflare) — Let's Encrypt проверяет домен по HTTP, и проксирование может
помешать первой выдаче. После выдачи проксирование можно включить.

Traefik запрашивает сертификат в момент создания маршрута. Если запись в DNS
появилась уже после деплоя, сертификат сам не подтянется — нужен передеплой
ресурса, тогда маршруты пересоздаются и выпуск повторяется.

## Первый деплой

1. **Проект и ресурс.** В Coolify создайте проект (например `rabbitfarm`), внутри —
   окружение `production`, затем `+ New Resource` → `Docker Compose` → источник
   `Public Repository` (или приватный, если репозиторий закрыт) и укажите
   `https://github.com/MubiZero/RabbitFarm`.
2. **Файл стека.** В настройках ресурса задайте
   `Docker Compose Location` = `docker-compose.coolify.yml`, ветку — `main`.
3. **Домены.** Coolify предложит домены для сервисов с `SERVICE_FQDN_*`.
   Проверьте, что у `web` стоит основной домен, а у `api` — поддомен `api.`.
   Оба должны указывать A-записями на сервер.
4. **Переменные.** Ничего обязательного задавать не нужно — всё либо
   генерируется, либо имеет разумное значение по умолчанию. Опционально:

   | Переменная | По умолчанию | Зачем менять |
   |---|---|---|
   | `MYSQL_DATABASE` | `rabbitfarm` | другое имя базы |
   | `MYSQL_USER` | `rabbitfarm` | другое имя пользователя |
   | `JWT_EXPIRE` | `15m` | срок жизни access-токена |
   | `JWT_REFRESH_EXPIRE` | `90d` | срок жизни refresh-токена: столько приложение можно не открывать и не входить заново |
   | `RATE_LIMIT_MAX_REQUESTS` | `100` | лимит запросов за окно |
   | `LOG_LEVEL` | `info` | подробность логов |
   | `TZ` | `Asia/Dushanbe` | часовой пояс контейнера: от него зависит, во сколько уходят ежедневные уведомления (08:00 местного времени) |
   | `RUN_SEEDS` | `false` | `true` — залить **демо-данные для разработки**: учётные записи с общеизвестными паролями, породы, клетки и корма. В продакшене сидер откажется работать. |
   | `ALLOW_REGISTRATION` | `false` | `true` — временно открыть регистрацию, чтобы завести ещё одну учётку |
   | `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY` | пусто | Push-уведомления (FCM). Опционально — без них сервис просто ничего не отправляет. Значения из service account ключа Firebase-проекта. |

5. **Deploy.** Первая сборка дольше обычного: собираются два образа, у Flutter
   прогревается кеш. Готовность видно по healthcheck — `api` становится
   `healthy` только после успешных миграций.

## Первый вход

`ALLOW_REGISTRATION` — плоский выключатель без исключения для первого раза:
`false` (значение по умолчанию из `.env.example`) отклоняет **любую**
регистрацию, включая самую первую. Поэтому сразу после первого деплоя
временно поставьте `ALLOW_REGISTRATION=true`, зарегистрируйтесь через сайт —
регистрация поднимает новую ферму и делает регистрирующегося её владельцем
(`authService.register`: `Farm.create` + пользователь с ролью `owner`,
привязанный к этой ферме) — и, если публичная регистрация новых ферм на этом
стенде не нужна, верните `false`.

Регистрация всегда заводит **новую отдельную ферму** — это правильный путь
для владельца отдельного хозяйства, не для сотрудника: каждый следующий
`ALLOW_REGISTRATION=true` + регистрация даёт ещё одну независимую ферму,
человек не увидит поголовье, клетки и задачи чужого хозяйства.

Чтобы добавить человека в **то же** хозяйство с общим доступом — используйте
приглашения (готовы, см. README → «Accounts»): владелец на экране «Работники»
выдаёт код, человек вводит его на `/join` и оказывается в той же ферме со
своей ролью (`manager`/`worker`). `ALLOW_REGISTRATION` для этого не нужен и не
подходит — держите его `false`.

## Проверка после деплоя

```bash
curl -fsS https://api.<ваш-домен>/health
```

Ответ `{"status":"healthy",...}` означает, что приложение поднялось и видит базу.
Дальше откройте `https://<ваш-домен>` — должен открыться экран входа.

## Ссылка-приглашение и магазины

Работника зовут ссылкой `https://<ваш-домен>/i` — одной и той же в SMS, в
письме и в пересылке через мессенджер. Адрес постоянный: он вшит в
одобренный шаблон SMS у payom, а шаблон там **не редактируется** — правка
текста означает новый `templateId` и новую модерацию.

Что за ним стоит, зависит от четырёх переменных сервиса `web`. Ни одна не
обязательна: без них ссылка просто открывает страницу с кнопкой «открыть в
браузере».

| Переменная | Откуда берётся |
|---|---|
| `APPLE_TEAM_ID` | Apple Developer → Membership |
| `ANDROID_CERT_SHA256` | Play Console → Setup → App signing → **App signing key certificate**, SHA-256 |
| `APP_STORE_URL` | адрес страницы приложения после публикации |
| `PLAY_STORE_URL` | то же для Google Play |

Отпечаток берётся именно от ключа, которым подписывает Google (Play App
Signing), а не от локального ключа сборки — иначе проверка не пройдёт у всех,
кто поставил приложение из магазина. Он появляется в консоли только после
первой загрузки сборки, поэтому до неё переменную просто не задают: файла
`assetlinks.json` тогда нет вовсе, и это честнее пустого.

Файлы проверки пишет `docker-entrypoint.d/40-links.sh` при старте
контейнера, так что смена значений — это Restart сервиса, а не пересборка.
Проверить после деплоя:

```bash
curl -fsS https://<ваш-домен>/.well-known/apple-app-site-association
curl -fsS https://<ваш-домен>/.well-known/assetlinks.json
```

Оба должны отдаваться с `content-type: application/json`, кодом 200 и **без
редиректов** — редирект Apple не принимает. Android проверяет связь при
установке; посмотреть результат на устройстве:

```bash
adb shell pm get-app-links dev.mubi.rabbitfarm
```

На стороне приложения домен объявлен в
[AndroidManifest.xml](../mobile/android/app/src/main/AndroidManifest.xml) и в
[Runner.entitlements](../mobile/ios/Runner/Runner.entitlements) — смена
домена требует правки обоих.

## Что важно знать

**Смена домена API требует пересборки web.** У Flutter web нет рантайм-конфигурации:
адрес API вшивается в бандл на этапе сборки (build-arg `API_URL`). Поменяли домен —
нажмите Redeploy у сервиса `web`.

**Загрузки лежат в MinIO, не на диске `api`.** Фотографии кроликов — объекты в
бакете `rabbitfarm-uploads` (сервис `minio`, том `minio-data`), а не файлы в
контейнере API — сам `api` можно пересоздавать без потери фото. Учётка —
`SERVICE_USER_MINIO`/`SERVICE_PASSWORD_MINIO`, генерирует и хранит Coolify,
как и пароли `db`. Том `minio-data` переживает передеплой, но не переезд на
другой сервер: при миграции его, как и `db-data`, нужно копировать отдельно.

**Логи живут в stdout, файлы — на постоянном томе.** Приложение пишет и в
stdout (его собирает Docker, видно в Coolify → `Logs`), и в файлы
`/app/logs/combined.log` и `/app/logs/error.log`. На ресурсе `api`
(Application → `Storages`) на `/app/logs` заведён персистентный том
(`rabbitfarm-api-logs`, управляемый Coolify) — файлы переживают передеплой,
в отличие от диска контейнера. Для разбора инцидента «на вчера» на несколько
серверов всё равно лучше отдельный сборщик логов, а не том на одном сервере.

**Часовой пояс контейнера — `Asia/Dushanbe`** (`TZ` в `backend/Dockerfile`).
От него зависят ежедневные задачи: дайджест уведомлений и напоминания об
окончании тарифа назначены на 08:00 местного времени. В UTC-контейнере они
уходили бы в 13:00 по Душанбе. Другой регион — переопределите `TZ` в
переменных ресурса.

**Миграции идут при каждом старте контейнера** и повторяются до 10 раз, если база
ещё не готова. Откатов на старте нет — это осознанно: автоматический откат на
проде опаснее упавшего деплоя.

**CORS настроен на домен `web`.** Если появится ещё один клиент (например,
отдельная админка), добавьте его домен в `CORS_ORIGIN` через запятую.

## Резервные копии

Копировать нужно **две** вещи, и вторую забыть особенно легко:

| Что | Где живёт | Чем снимается |
|---|---|---|
| База | том данных MySQL | `mysqldump` → gzip, [`scripts/backup-db.sh`](../scripts/backup-db.sh) |
| Фотографии | том MinIO | `mc mirror`, [`scripts/backup-uploads.sh`](../scripts/backup-uploads.sh) |

В базе лежит только путь к файлу — сам снимок хранится в MinIO. Дамп базы без
зеркала бакета восстановит карточки кроликов без единой фотографии.

Оба скрипта запускаются **внутри** соответствующего контейнера: там уже есть и
нужный инструмент (`mysqldump` / `mc`), и пароли в переменных окружения, так
что секреты не переезжают в расписание и не светятся в логах.

```bash
docker exec <контейнер-db>    sh -c "$(cat scripts/backup-db.sh)"
docker exec <контейнер-minio> sh -c "$(cat scripts/backup-uploads.sh)"
```

В Coolify — `Scheduled Tasks` на соответствующем ресурсе, тело скрипта целиком,
расписание `0 3 * * *` для базы и `30 3 * * *` для фотографий.

**Каталогу `/backups` нужен постоянный том.** Без него копии лежат на диске
контейнера и исчезают при ближайшем передеплое — расписание при этом исправно
отрабатывает каждую ночь, и пробел заметен только в тот день, когда копия
понадобится. И это не `/var/lib/mysql`: рабочий каталог базы — не место для
архивов.

Хранятся последние 14 дампов (`BACKUP_KEEP`), зеркало фотографий повторяет
бакет один в один: удалённое в хранилище удаляется и в зеркале.

### Восстановление

```bash
# База — разворачивать в отдельную базу, а не поверх рабочей
gunzip < /backups/rabbitfarm-ГГГГ-ММ-ДД-ЧЧММСС.sql.gz \
  | mysql -u root -p"$MYSQL_ROOT_PASSWORD" имя_базы

# Фотографии — обратным зеркалированием
mc mirror --overwrite /backups/uploads backup-local/rabbitfarm-uploads
```

Процедура проверена целиком 2026-09-13 на локальном стенде: дамп снят и
развёрнут в отдельную базу (29 таблиц, все количества строк совпали с
источником), 36 объектов ушли в зеркало и вернулись в отдельный бакет с
совпадающей контрольной суммой файла. На боевом стенде восстановление не
прогонялось — там живые данные фермы.

### Что включено на боевом стенде (2026-09-13)

**Фотографии — да.** На сервисе `rabbitfarm-minio` заведён том
`minio-backups` на `/backups` и задача `backup-uploads` (ежедневно в 03:30,
контейнер `minio`, таймаут 600 с) с телом из
[`scripts/backup-uploads.sh`](../scripts/backup-uploads.sh). Проверено
запуском вручную: задача отработала успешно, `/backups` — настоящий том на
диске хоста, а не слой контейнера.

Бакет на проде на момент настройки был **пуст**: ни одной фотографии за всё
время. Это ожидаемо — отдача фото была сломана до 2026-09-13 (см. историю
коммитов), и загружать их было бессмысленно.

**База — нет.** Настраивается в панели, вкладка `Backups` у ресурса
`rabbitfarm-db`: имя базы для дампа — **`default`** (не `rabbitfarm`),
расписание `0 3 * * *`, хранить 14 копий. Через API это делать нельзя:
эндпоинт `/databases/{uuid}/backups` отдаёт записи чужих ресурсов — на запрос
бэкапов нашего MySQL он возвращает бэкап PostgreSQL другого проекта
(`database_type=StandalonePostgresql`). Запись через него может уехать не туда,
поэтому здесь — только руками через интерфейс.

### Чего ещё нет: выгрузки наружу

Копии лежат на том же сервере, что и данные. Это спасает от «удалил не ту
запись» и не спасает от потери сервера: диск, аккаунт у хостера или ошибочный
`docker volume rm` уносят оригинал и копию одним движением.

Выгрузку наружу нужно завести отдельно — это требует учётки у стороннего
хранилища (Backblaze B2, Cloudflare R2, любой S3). Каталог `/backups` намеренно
общий для обоих контейнеров: дампы базы и зеркало фотографий лежат рядом,
поэтому наружу всё уходит одной командой из контейнера MinIO — там есть `mc`:

```bash
mc alias set offsite https://<endpoint> <ключ> <секрет>
mc mirror --overwrite --remove /backups offsite/<бакет>/rabbitfarm
```

Проверено 2026-09-13, что контейнер MinIO действительно видит дампы базы в
общем томе. Сама выгрузка не настроена: нужен выбор хранилища и реквизиты.

**Если прод собран не из этого compose-файла** (сейчас так и есть: MySQL,
MinIO и приложения заведены в Coolify отдельными ресурсами), том `/backups`
добавляется каждому из двух ресурсов через `Storages` в панели — описанные
выше команды от этого не меняются, они работают внутри контейнера и про
устройство стенда ничего не знают.

## Локальная разработка

Прод-стек трогать не нужно, для локального запуска есть отдельный файл:

```bash
docker compose up -d
```

Он читает секреты из `.env` в корне (в git не попадает, шаблон —
[`backend/.env.example`](../backend/.env.example)) и, в отличие от прод-стека,
публикует порты наружу: база на `3307`, API на `4567`.
