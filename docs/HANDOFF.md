# Handoff: состояние на 2026-09-08

Кратко — что сделано, что настроено локально и не попало в git, что дальше.
Пишется для продолжения работы с другого устройства.

## Что готово и закоммичено

- **MinIO** — файлы (фото кроликов) хранятся в S3-совместимом MinIO вместо
  локального диска, отдаются через прокси-роут API. Живая проверка через
  докер-стек пройдена (upload → fetch → delete → 404).
- **Эсхата Мерчант** — платёжный клиент (подпись SHA-256, dynamic-kassa,
  создание заказа + проверка статуса), модель `Payment` (tenant-scoped),
  сервис `paymentService` (webhook никогда не доверяется без перепроверки
  подписанным запросом к банку), контроллер, роуты. **Живьём проверено**
  против тестового контура банка (create + status — реальные ответы банка).
- **Payom SMS** — транспорт для шаблонных SMS, templateId берётся из
  конфига (`SMS_TEMPLATE_IDS`), не хардкодится. Постоянные ошибки
  (401/403/422) не ретраятся, временные (429/5xx/сеть) помечены retryable.
  **Реальная отправка подтверждена живьём** (2026-09-07): IP разработчика
  добавлен в вайтлист Payom напрямую (не через Tailscale — обычная сеть),
  SMS дошла на реальный номер, `deliveryStatus: SERVICE_ACCEPTED`. Шлюз
  требует номер строго в формате `+992XXXXXXXXX` (с `+`, 13 символов) —
  без плюса 422. Для повторной ручной проверки: `backend/scripts/test-payom-sms.js`.
- **Тесты**: 1200/1200 зелёных, 69/69 сьютов. Попутно найден и исправлен
  реальный кросс-платформенный баг — `testDb.js` дёргал
  `node_modules/.bin/sequelize-cli` (shell-shim), что падает с ENOENT на
  Windows и никогда не ловилось в CI (CI на ubuntu-latest). Теперь миграции
  тестовой БД запускаются через `node` напрямую по JS-файлу пакета.
- **Сброс пароля по коду (SMS/email)** — владелец фермы раньше не мог сам
  восстановить пароль (`resetMemberPassword` исключает роль `owner`), а
  единственный самостоятельный путь ничего никуда не отправлял. Теперь
  `forgotPassword`/`resetPassword` генерируют 6-значный код (не 32-байтный
  токен — тот было не набрать руками), шлют его по SMS (если есть телефон)
  или email (иначе), с блокировкой после 5 неверных попыток и сроком жизни
  15 минут. Email — через собственный SMTP (Stalwart, `mail.mubi.dev`),
  `backend/src/services/notifications/emailTransport.js` (nodemailer).
  Мобильный клиент: `/forgot-password` → `/reset-password`, кнопка вместо
  прежней статичной надписи на логине. **Живьём проверено** через реальный
  docker-стек (создание кода, инкремент попыток, блокировка после 5 раз) —
  сама доставка email пока не проверена, см. «Дальше».
  Попутно найден и исправлен реальный пробел в проде: `docker-compose.yml` и
  `docker-compose.coolify.yml` вообще не прокидывали `ESKHATA_*`/`SMS_*` в
  контейнер `api` — платежи и SMS были неработоспособны при любом деплое
  через docker-compose, хотя тестировались вручную мимо него.

## Настроено локально, НЕ в git (перенести на другое устройство вручную)

`backend/.env` (гитигнорится) содержит реальные тестовые креды:
- `ESKHATA_*` — тестовый контур банка (id организации, merchID, hash key).
- `SMS_API_TOKEN` — реальный токен Payom, `SMS_TEMPLATE_IDS` — маппинг
  `user.verification_code` → готовый templateId.

Актуальные плейсхолдеры и комментарии — в `backend/.env.example`. Значения
самих секретов у пользователя (не хранятся в репозитории намеренно).

## Известное ограничение окружения

Эсхата (`connecttest.eskhata.com`) банит доступ по IP с обычной сети
разработки — живая проверка сделана через Tailscale exit node (`honor-win`):
включить `tailscale set --exit-node=<name>`, выключить после
`tailscale set --exit-node=`. Payom (`gateway.payom.tj`) банил так же, но
решается проще — обычный вайтлист IP в кабинете Payom, без обхода через VPN.
IP разработчика похож на динамический (менялся в пределах одной сессии) —
если снова словите 403 с `IP-block`, вайтлист нужно обновить на актуальный.

## Дальше (по приоритету)

   (`mail.mubi.dev`) — предполагаемый адрес `rabbitfarm@mubi.dev`. Раз
   `postmaster@mubi.dev` уже принимает DMARC-отчёты, SPF/DKIM для этого
   домена, похоже, уже настроены — сначала проверить в панели, возможно
   нужен только новый ящик, а не полный ранбук «новый домен». После —
   заполнить `SMTP_*` в `backend/.env` (и в `.env`/Coolify для реального
   деплоя) и живьём проверить доставку (Authentication-Results, mail-tester.com).
2. Согласовать с банком реальный формат webhook-пейлоада перед боем — сейчас
   поле `invoiceId` в `paymentController.webhook` это предположение по спеке.

   в платформенной админке) + **Платформенная админка** (вариант A —
   in-app суперадмин, но удобнее базового). Payment/Farm уже есть как база
   для подписочной логики.

   международного. Масштабирование — только как варианты на обсуждение, без
   реализации (MinIO — единственный уже сделанный "дешёвый сейчас" шаг).
