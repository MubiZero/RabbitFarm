# Бэклог: сверка с лучшими практиками отрасли

Список пунктов, найденных при сравнении RabbitFarm с тем, как устроены
крупные SaaS — по аспектам, один раздел на аспект. Не план с датами и
оценками (как `PLATFORM-ADMIN.md`), а сырой список наблюдений: что стоит
сделать, когда дойдут руки, и почему.

Статусы: `[ ]` не начато, `[~]` в работе, `[x]` сделано.

## Биллинг и тарифы (сверка 2026-09-10)

- [x] **Напоминания после просрочки, не только до.** Сейчас `planExpiryReminderJob`
  шлёт push/email за 7 и за 1 день до истечения, а после перехода в
  `read_only` — тишина, только пассивный баннер в приложении. Индустрия
  держит 1-2 напоминания и после (например, день 3 и день 14) — это прямая
  недополученная выручка, а стоит несколько строк в уже существующей job.
- [ ] **Квитанция клиенту после оплаты.** Не PDF-инвойсинг, а минимум:
  email с суммой/датой/номером платежа. Не актуально, пока нет платящих
  клиентов, но должно быть готово к первому реальному платежу — фермам
  как ИП/юрлицам обычно нужен документ для бухгалтерии.
- [x] **Короткий grace-буфер (несколько часов) после `plan_expires_at`**
  перед переходом в `read_only`, на случай задержки подтверждения платежа
  банком. Сейчас переход день в день.
- [x] Проверить, что `Payment` хранит достаточно полей, чтобы посчитать
  MRR/ARR позже без миграции (сумма, дата, farm_id, план на момент оплаты) —
  если да, это просто отложенный экран, а не отложенная архитектура.
  Проверено: плана на момент оплаты не хватало — добавлено поле `plan`
  снимком (не FK на `plans`, план мог смениться/переименоваться).

## Онбординг и активация (сверка 2026-09-10)

- [x] **Баг: название фермы теряется между онбордингом и регистрацией.**
  `onboarding_ready_screen.dart` показывает «{name} готова к работе!» из
  `onboardingProvider`, но `register_screen.dart` заводит своё поле
  `_farmNameController` пустым, не читая это же состояние. Если человек не
  перепечатает имя вручную, бэкенд (`authService.js`) подставит дефолт
  `Ферма ${full_name}` — не то имя, которое только что показали как готовое.
  Обещали одно, сохранили другое, в первую минуту знакомства с продуктом.
  Фикс точечный: прокинуть `onboardingProvider.farmName` в форму регистрации.
- [ ] **`farmType` («один» / «с командой») собирается и не используется
  нигде.** Ни на бэкенд не уходит, ни на один экран не влияет (нет ветвления
  вроде «один — скрыть приглашение сотрудников»). Вопрос задан, ответ
  выброшен — либо убрать шаг, либо реально на него опереться.
- [ ] **Тур на «Сегодня» объясняет виджеты, а не ведёт к первому действию.**
  2 шага coach-mark показывают блок алертов и блок статистики — на пустой
  ферме оба пустые, объяснять там нечего. Индустрия ведёт новичка к
  «aha moment» (первое реальное действие: добавить кролика/клетку), а не
  к экскурсии по интерфейсу.
- [ ] **Нет чек-листа активации** (добавьте клетку → кролика → первую
  запись кормления, с видимым прогрессом). По бенчмаркам такие чек-листы
  дают ощутимо более высокую активацию в первую неделю, чем расчёт на то,
  что пользователь сам найдёт дорогу через пустые состояния списков.
- [ ] **Структурный вопрос — шаги онбординга идут ДО регистрации, а не
  после.** Ровно из-за этого порядка две независимые формы «имя фермы» не
  знают друг о друге (см. первый пункт). Практика — короткая регистрация
  первой, сбор контекста и настройка потом, как часть первого запуска уже
  авторизованного пользователя, встроенная в реальные экраны.

## Разделение ролей внутри фермы (сверка 2026-09-10)

- [x] **Приглашение сотрудника — только по email.** `staffValidator.js`
  требует `email`, телефона как альтернативы нет — при том, что у продукта
  уже есть рабочая SMS-инфраструктура (Payom), а целевой работник фермы
  вероятнее имеет телефон, чем почту. Стоит добавить приглашение по
  телефону тем же путём, что уже есть для SMS-уведомлений.
- [x] **Нет видимого журнала смены ролей/деактивации/передачи владения
  внутри фермы** — только `logger.info` в стдаут контейнера
  (`staffService.js`). Тот же класс пробела, что уже закрыт на уровне
  платформенной админки через `admin_audit_log` (см. PLATFORM-ADMIN.md,
  1.1) — паттерн есть в кодовой базе, просто не переиспользован для
  действий владельца фермы над своими сотрудниками. Владелец сейчас не
  может узнать «кто и когда понизил Петра до worker», не имея доступа к
  серверным логам.

Что уже сделано хорошо и трогать не стоит: RBAC-модель с capability-слоем
на клиенте ([farm_access.dart](mobile/lib/core/access/farm_access.dart)),
least-privilege по умолчанию при приглашении (роль `worker`), передача
владения атомарной транзакцией, криптостойкие токены приглашений с TTL.

## Безопасность и обработка ошибок (сверка 2026-09-10)

- [x] **Валидация загруженных файлов — по заявленному `Content-Type`, не по
  содержимому.** `multer.js` сверяет `file.mimetype` (клиент сам его
  выставляет), не байты файла — OWASP считает это проверкой данных,
  контролируемых атакующим. Сейчас не эксплуатируется только потому, что
  `helmet()` ставит `nosniff` глобально и SVG нет в `ALLOWED_FILE_TYPES` —
  случайно совпавшая защита, не намеренная. Стоит либо программно запретить
  SVG независимо от `.env`, либо добавить проверку magic bytes при загрузке
  (пакет `file-type`, несколько строк).
- [x] **На мобилке нигде нет `runZonedGuarded` / `FlutterError.onError` /
  `PlatformDispatcher.instance.onError`.** Это не про отсутствие Sentry —
  это про то, что даже бесплатный встроенный перехват ошибок Flutter не
  подключён. Ошибка вне дерева виджетов (необработанный `Future`) падает
  молча — ни в лог, ни куда-либо ещё. Стоит добавить в первую очередь, ещё
  до решения о крэш-репортере: подключить перехват дёшево, а куда слать
  данные — отдельный вопрос.
- [x] **Нет `ErrorWidget.builder`** — падение при сборке виджета в релизе
  показывает пользователю стандартный экран ошибки Flutter вместо своего
  «что-то пошло не так».
- [ ] Держать в уме при расширении списка типов файлов: если когда-нибудь
  понадобится `image/svg+xml` (логотипы, иконки) — `nosniff` от XSS через
  SVG не защищает, там нужна отдельная проверка/санитайзинг.

Что уже сделано на уровне, выше среднего для такого масштаба: timing-safe
сравнение пароля при логине по несуществующему email (защита от
enumeration по времени ответа), `uncaughtException`/`unhandledRejection`
на бэкенде логируются и завершают процесс (а не продолжают жить в
неизвестном состоянии), CORS-allowlist и заголовки безопасности на nginx
задокументированы с историей, зачем они именно такие.

## Офлайн и синхронизация (сверка 2026-09-10)

Текущее состояние подтверждено в `docs/ARCHITECTURE.md:213` и коде: online-only,
ни `sqflite`/`hive`, ни детектора связи, ни очереди — осознанное ограничение
MVP. `StaleDataBanner` смягчает только в рамках текущей сессии (in-memory),
не переживает перезапуск приложения.

- [x] **Уровень 0 — кэш чтения, переживающий перезапуск.** Последний
  успешный ответ по спискам (стадо, клетки, задачи) — в Hive/sqflite, а не
  только в памяти Riverpod. Дёшево, снимает самый частый случай: зашёл в
  сарай без связи, открыл уже виденный список.
- [x] **Уровень 1 — проактивный детектор связи.** `connectivity_plus` +
  баннер на уровне всего приложения (по образцу уже существующих
  `ImpersonationBanner`/`FarmStatusBanner` в `main.dart`), вместо того
  чтобы узнавать про офлайн только по ошибке каждого отдельного запроса.
- [ ] **Уровень 2 — офлайн-очередь только для действий из
  `FarmCapability.recordDailyWork`** (кормление, отметка задачи, заметка):
  это операции добавления, часто происходят именно в поле, низкий риск
  конфликта. Разрешение конфликта — простое «побеждает последняя запись
  по времени», без CRDT (оверинжиниринг для этого масштаба). Граница
  капабилити из разбора ролей естественно совпадает с границей, где
  офлайн-запись оправдана.
- [ ] **Сознательно не расширять офлайн на:** транзакции, управление
  сотрудниками, создание/редактирование кроликов и клеток — редкие
  операции либо требующие актуального состояния сервера, либо и так за
  manager/owner, которые реже работают без связи в моменте.

## Мониторинг и наблюдаемость (сверка 2026-09-10)

- [x] **Критично: в проде backend не пишет ничего в stdout.**
  `logger.js` добавляет консольный transport только при
  `NODE_ENV !== 'production'`, а `Dockerfile:20` прошивает
  `NODE_ENV=production` в образ. Все логи (включая HTTP-access через
  morgan) идут только в файлы внутри контейнера. Плюс: файлы логов не
  смонтированы на реальном Coolify-ресурсе (`docker-compose.coolify.yml`
  по собственному примечанию в файле больше не источник для деплоя,
  `docs/DEPLOY.md` не описывает volume для логов на актуальном ресурсе).
  Итог — стандартная панель логов Coolify, скорее всего, пуста, и любой
  редеплой (несколько раз в день по факту) стирает файлы с диска
  контейнера. Первый шаг — вернуть stdout в проде (убрать/заменить условие
  `NODE_ENV !== 'production'`), это одна строка и сразу окупается.
- [ ] Смонтировать `logs/` как постоянный volume на самом Coolify
  Application-ресурсе — пока нет внешнего сборщика логов. Требование
  задокументировано в `docs/DEPLOY.md`, сама настройка — действие в
  панели Coolify, не в коде.
- [x] **Найдена связь с биллингом:** `planExpiryReminderJob.js` аккуратно
  ловит все ошибки и пишет `logger.error`, но при текущей конфигурации это
  никуда не долетает — если job молча начнёт падать, единственный сигнал
  будет «клиенты перестали платить», а не алерт. Вся ценность работы над
  напоминаниями об оплате обесценена этим же пробелом. Закрыто тем же
  фиксом, что и пункт про stdout выше — `logger.error` теперь виден в
  Coolify → Logs.
- [ ] Sentry (или аналог) на бэке и мобилке — уже отмечено в первом
  аудите готовности, здесь подтверждено: без пункта про stdout выше даже
  Sentry не закроет всё (`logger.error` по бизнес-логике без исключения в
  Sentry не попадёт без отдельной интеграции с Winston).
- [ ] Минимальный алертинг на 2-3 события уже сейчас: health-check падает
  несколько раз подряд, ошибка в cron-джобах, рост 5xx — вебхук в
  мессенджер, не обязательно полноценный дашборд.
- [x] Раздел «Metrics» в `docs/ARCHITECTURE.md` (response time, error
  rate, active users, DB query performance) читается как список готовых
  возможностей, но ни один пункт не реализован (нет prometheus/datadog/
  newrelic в зависимостях). В отличие от соседней строки про Sentry, это
  нигде не помечено как план, а не факт — стоит либо явно пометить, либо
  убрать, чтобы не вводить в заблуждение. Помечено как план.

## Уведомления (сверка 2026-09-10)

- [x] **Таймзона не задана нигде** (`Dockerfile`, `docker-compose*.yml`,
  `docs/DEPLOY.md`) — `notificationDigestJob.js` и `planExpiryReminderJob.js`
  оба рассчитаны на «08:00 время суток» по собственному комментарию в коде,
  но контейнер живёт в UTC, то есть реально стреляют в 13:00 в Душанбе.
  Дёшево чинится: `TZ=Asia/Dushanbe` в окружении или явный `timezone` в
  опциях `node-cron`.
- [ ] **Нет ни одной настройки уведомлений у пользователя.** В
  `settings_screen.dart` только тема и акцент. Не строить сразу полный
  preference-center (канал × категория × тихие часы) — оверинжиниринг для
  масштаба; начать с одного переключателя «получать дайджест вкл/выкл»,
  остальное — по факту жалоб.

Что уже хорошо: батчинг дайджеста продуман по смыслу, а не только для
экономии — просроченные вакцинации/корм идут одним пушем в сутки, а
персональная задача с исполнителем — точечно ему одному
(`notificationDigestJob.js`, см. комментарий в коде).

## Рост и удержание (сверка 2026-09-10)

Сигнал «ферма не заходит N дней» уже есть, но виден только суперадмину
(`platformAdminService.js`, фильтр в сводке платформы) — дальше никуда
автоматически не ведёт. Продуктовой аналитики нет вообще (ни Firebase
Analytics, ни Amplitude/PostHog/Mixpanel), реферальной механики,
шаринга и промпта на оценку в сторе — тоже нет. Это ожидаемо для стадии
без единого платящего клиента — большинство пунктов здесь rightly
отложены, кроме одного.

- [x] **Подключить минимальную аналитику сейчас, до прихода реальных
  пользователей, а не после.** Единственный пункт в этом разделе, который
  дороже добавить задним числом, чем заранее — данные, не собранные до
  открытия регистрации, не восстановить. Firebase Analytics бесплатен и
  `firebase_core` уже в зависимостях (используется для push). Минимум:
  регистрация завершена, первый кролик добавлен, первая запись кормления,
  посещение каждой из 5 вкладок оболочки. Напрямую нужно для проверки
  гипотез из раздела «Онбординг и активация» (какое действие в первую
  неделю предсказывает, что ферма останется).
- [x] **Win-back по неактивности — автоматизировать то, что уже видно
  админу вручную.** Переиспользовать существующую инфраструктуру
  (`notificationService`, тот же принцип, что у дайджеста и напоминаний об
  оплате): push/email на 14/30 день неактивности фермы. Не новая система,
  а ещё один сценарий поверх готового.
- [ ] Реферальная механика, программы лояльности, промпт на оценку в
  сторе — сознательно отложить до появления базы активных ферм, как и
  MRR-графики в биллинге. Промпт на оценку (`in_app_review`) — самый
  дешёвый из всех, можно вернуться к нему первым, когда дойдут руки.

## Политика конфиденциальности (сверка 2026-09-10)

Черновик готов: [mobile/web/privacy.html](../../mobile/web/privacy.html) —
статическая страница, попадает в веб-сборку автоматически (nginx отдаёт
`mobile/web/*` как есть), доступна по `/privacy.html` на домене веб-приложения.
Ссылка на неё добавлена в Настройки → О приложении
(`settings_screen.dart`). Содержание основано на реальном сборе данных в
коде (таблица моделей `User`/`Payment`/`DeviceToken`/`AdminAuditLog`,
интеграции Firebase/Payom/банк «Эсхата»), не придумано.

- [ ] **Заполнить плейсхолдеры перед публикацией:** юридическое
  название/адрес оператора, email и телефон поддержки — в файле помечены
  `[В КВАДРАТНЫХ СКОБКАХ]`.
- [ ] **Показать юристу, знакомому с законодательством Таджикистана**,
  прежде чем считать документ окончательным — черновик грамотный по
  общей практике (что требуют App Store/Google Play), но не проверен на
  соответствие местным нормам о персональных данных.
- [ ] **Добавить чекбокс согласия на экране регистрации** — сейчас
  `register_screen.dart` не ссылается на политику вообще. Стоит сделать
  после того, как текст пройдёт юридическую проверку и утратит плейсхолдеры
  — чтобы не завязывать обязательное согласие на черновик.
- [ ] Заодно закрывает пункт из раздела «Разделение ролей» и «Онбординг» —
  теперь есть куда сослаться, объясняя, какие данные видит платформенный
  админ при входе под клиентом (уже упомянуто в самом тексте политики).

## Поддержка пользователей (сверка 2026-09-10)

Прогрепал весь код — фраза «обратитесь в поддержку» встречается минимум в
трёх местах (`subscriptionNoPlanHint`, `farmStatusBannerSuspended`, подсказка
в диалоге impersonation), но ни разу рядом нет реального канала — ни email,
ни телефона, ни телеграма. Совпадение `@rabbitfarm` в `docs/API_TESTING.md`
оказалось тестовыми учётками (`admin@rabbitfarm.com`), не настоящим
контактом. Спросил, какой канал сделать официальным — решение не принято,
рассматривается вариант обойтись без внешнего канала вовсе.

- [~] **Не строить внешний Zendesk/Intercom — при нуле клиентов не для
  кого.** Вместо этого — маленькая сквозная фича «Обращение в поддержку»,
  ложится на уже существующий паттерн платформенной админки (вкладки
  фермы/тарифы/объявления → плюс «Обращения»):
  - [x] Бэкенд: таблица `support_requests` (farm_id, user_id, текст, статус
    new/resolved, время), `POST /support-requests` (любая роль фермы,
    работает даже при закрытом доступе фермы), `GET /platform-admin/support-requests`
    + `PATCH .../:id/resolve`.
  - [ ] Мобилка (фермер): экран «Написать в поддержку» — из Настроек и вместо
    голого текста в местах, где сейчас просто написано «обратитесь в
    поддержку». **Не сделано.**

## API-версионирование и обратная совместимость (сверка 2026-09-10)

- [x] **Нет способа сказать старому клиенту «обновитесь».** `API_VERSION` —
  только префикс URL, не механизм сосуществования версий; нет проверки
  минимальной версии приложения на бэкенде, нет `X-App-Version`, нет
  force-update экрана. Не проблема, пока приложение не опубликовано в
  сторах — но обновление в сторе доходит до части пользователей с
  задержкой в дни, а бэкенд деплоится по нескольку раз в день. Сделать
  до публикации в App Store/Google Play: `PackageInfo` на клиенте +
  простая проверка минимальной версии в middleware (не многоверсионная
  маршрутизация, просто «обновитесь»).
